# Desktop data sources

The desktop starts with an empty library and task queues, then scans the configured Minecraft directory. It no longer seeds sample instances, accounts, download progress, play time, or AI tasks. Static feature cards are usage guides, and the changelog describes the current development build without fabricated release dates.

## Local games and launching

Open **设置 → 游戏设置** to manage multiple instance collection folders containing `versions`, `libraries`, and `assets`. Use **新建 / 导入** to create a folder (an existing folder is imported without modifying its contents), or **浏览导入…** to select an existing folder. New folders are suggested alongside the current collection; on a fresh installation the default is `.minecraft` beside the launcher executable. Existing saved game directories are retained. Removing a folder only removes its registration. Choose **设为当前**, select a Java runtime and memory mode, then click **保存并应用** to persist settings and rescan the current collection. The homepage shows instances from that collection. **环境配置** remains an entry to the same page. The scanner also accepts the legacy `version` directory.

The Java dropdown shows detected major/full versions and executable paths, plus **导入电脑中已有的 Java…**. Detection checks PATH/JAVA_HOME, common vendor folders, user JDK folders, collection runtimes, and common Minecraft folders on fixed local Windows disks. It is bounded and runs asynchronously with hidden probe processes. Identical executable paths are deduplicated; different JDK/JRE installations remain individually selectable. Import accepts `java.exe`/`javaw.exe` (the latter is normalized to its sibling `java.exe`); a failed import preserves the selection. Imported paths are persisted and included in later scans. **刷新 Java 列表** repeats discovery; **检测 Java** probes a manually entered executable.

New configurations default to **自动配置** memory. The automatic maximum heap is the smaller of one quarter of physical RAM, half of currently available RAM, and 16 GiB, rounded down to 128 MiB units with a 128 MiB minimum. **自定义** uses a 1–90% slider based on total physical memory. The panel refreshes total/used/available memory every three seconds while visible and shows the projected game allocation. Every actual launch reads a fresh memory snapshot and resolves `-Xms`/`-Xmx` from the saved mode; it does not reuse the UI estimate. Automatic allocation caps 32-bit Java at 1.5 GiB; excessive manual allocations report an error. Custom allocations larger than currently available RAM are rejected at launch. No system processes or working sets are modified. Unsaved edits and failed saves preserve the active launch configuration.

Java requirements come from installed version metadata. Mod counts include JAR files in each isolated version's `mods` directory. A present client JAR is not a complete dependency check: launching validates the selected account, Java, libraries, assets, and natives through `mc-core::GameLauncher`. The UI reports preparation errors, the process ID and log path, and the final exit code. Play time remains “未记录” because no play-time database exists.

Game settings are saved to `%LOCALAPPDATA%\MemoriaLauncher\environment.json`. Existing files without `memory_mode` retain their exact fixed MiB limits (or the previous 512/4096 MiB defaults) until the user selects automatic mode or moves the custom slider. `memory_mode`, `memory_percent`, and imported `java_paths` are saved alongside the existing fields. `MC_LAUNCHER_GAME_DIR` and `MC_LAUNCHER_JAVA` override saved settings at startup. `MEMORIA_DATA_DIR` overrides the launcher's data directory for development and isolated verification.

## Microsoft accounts

The core already implements PKCE authorization, Minecraft ownership checks, and token refresh. The desktop now supplies browser opening, a loopback HTTP callback, account selection, persistence, and logout.

For a locally registered application, open **设置 → 账户登录**, enter the application client ID and matching callback URI, and click **保存登录配置**. The configuration takes effect immediately and is reloaded after restart from `microsoft-login.json` in the launcher data directory. The account dialog's **配置 Microsoft 登录** button opens this page. Invalid input and save failures preserve the last active configuration. Changing the client ID requires signing in existing accounts again.

Saved local configuration takes priority over runtime environment variables, which take priority over the publisher's ID embedded through `MEMORIA_MICROSOFT_CLIENT_ID` at build time. Release builds can still embed the publisher's ID so players only click the Microsoft login button. Without saved local configuration, developers can also configure the application at runtime:

```powershell
$env:MC_LAUNCHER_CLIENT_ID = "your-application-client-id"
$env:MC_LAUNCHER_REDIRECT_URI = "http://localhost:53682/oauth/callback"
cargo run --locked -p desktop
```

The redirect URI defaults to the value above when omitted. Desktop callbacks support HTTP on `localhost` or `127.0.0.1`; the listener binds only to loopback, validates the callback path and OAuth state, and times out after three minutes. Login can be cancelled from the account dialog. Missing configuration, occupied ports, rejected authorization, and credential-storage errors are displayed in that dialog.

Account names, UUIDs, and the active account are saved in `accounts.json` in the data directory. Refresh tokens are stored separately in Windows Credential Manager under `MemoriaLauncher/Microsoft/<account-id>`. Access tokens remain transient. Logout deletes the corresponding vault entry. Other operating systems currently report that secure credential storage is unavailable.

## Download settings and vanilla installation

Open **设置 → 下载安装** to choose Mojang official servers, BMCLAPI, or a custom mirror implementing BMCLAPI's directory structure. Set parallel file downloads to 1–64 (default 8), then click **保存并应用**. Settings are saved atomically to `downloads.json` in the same launcher data directory as `environment.json`. Missing fields use defaults; invalid files are reported on the settings page. Failed saves preserve the active configuration. **检测连接** tests the draft source without saving it. Saving invalidates the catalogue cache; replies from the previous source are ignored. New jobs use the saved configuration; an installation already running keeps its original client and request limit.

The download page loads Mojang's version manifest through the selected source with a 30-second metadata timeout. Release IDs, snapshot IDs, publication timestamps, and metadata URLs come from that response. Unavailable descriptions, Java requirements, third-party loader compatibility, and hardware requirements are not synthesized. Failed requests display an error and can be retried without falling back to samples. Source URL routing follows the [BMCLAPI documentation](https://bmclapidoc.bangbang93.com/): metadata/client paths keep their paths, libraries use `/maven`, and resource objects use `/assets`. Unrelated hosts remain unchanged. BMCLAPI attribution is visible in the download settings. Custom remote sources require HTTPS; loopback HTTP is accepted for local testing.

**安装此版本** installs a standalone vanilla client into the current collection. The manifest checksum verifies the version JSON; file descriptors verify client, library, native, asset-index, resource and logging files. Existing files with matching checksums are reused. Streaming downloads share a semaphore held until the response body has been consumed, including across batches using the same client. Files are written to temporary siblings and renamed only after size/checksum validation; failures preserve the previous destination. The version JSON is published only after its dependencies finish, then the desktop rescans the collection. Modified existing version configurations are preserved and reported rather than overwritten. The download page and home queue show actual file completion counts. One installation runs at a time; collection changes and game launching wait for it to finish. Game-file requests have a five-minute timeout. Pause/resume is not implemented.

BMCLAPI does not serve the tested log XML object endpoint, so log XML files stay on their official Mojang URLs while still sharing the download limit. Inherited loader versions and old virtual/map_to_resources asset layouts remain unsupported. Full Microsoft login and game launching still use the existing authenticated runtime.

Desktop third-party resource catalogues remain unavailable. AI supports optional OpenAI-compatible chat. **设置 → AI 设置** consolidates the endpoint, model and masked API key controls. **保存并应用** stores the endpoint/model and a credential reference atomically in `ai.json`; the API key lives in Windows Credential Manager under `MemoriaLauncher/AI/<uuid>`. Startup reloads both. Unsaved drafts and failed saves preserve the active configuration; in-flight requests keep their original configuration. Clearing the key and saving removes the stored secret. Missing/unreadable saved credentials block requests until reconfigured. **测试连接** explicitly sends a short greeting using the draft configuration without saving it. Abnormal process exits offer opt-in analysis of the current run's redacted launcher log tail; logs are sent only after the user submits them from the AI page. The separate `mc-mcp` server exposes read-only real catalogue, local scan, and bounded instance log tools to external agents. Desktop download settings do not change MCP's read-only requests. Web search and AI installation/local mutation remain unavailable; actions never insert simulated work into the queues. General setting switches outside game/download/AI/account management retain their existing session-only behavior.

## Verification

```powershell
cargo check --workspace --locked --offline
cargo test --locked --offline -p desktop -p mc-core -- --test-threads=1
cargo test --locked --offline -p mc-core official_catalog_is_reachable -- --ignored
cargo test --locked --offline -p mc-core --test download_tests live_sources_download_real_metadata_with_checksum_verification -- --ignored --nocapture
```

The ordinary tests cover file-backed scanning, game/download/AI configuration reload, missing game directories/JARs, account persistence, callback state validation over a real loopback connection, Windows vault save/refresh/delete, and page interactions. A loopback HTTP fixture checks actual concurrent request counts with delayed bodies, source routing, verified-file reuse, transient HTTP retry, failed-checksum preservation, and a complete small vanilla installation followed by scanning. A separate loopback AI fixture reloads the persisted profile and vault key, executes the actual UI submission task, verifies the endpoint path, model and Authorization header, and delivers the response to the UI. This does not establish connectivity to a user-selected external model provider. The explicitly ignored live download test uses both source configurations to fetch real version metadata, an asset index, a small library and a small resource object, verifying their checksums; log XML remains on the official source. Full Microsoft login and game startup require a registered application, an eligible user account, Java, and installed game files; offline tests do not establish that end-to-end outcome.
